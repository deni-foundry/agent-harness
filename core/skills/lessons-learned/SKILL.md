> Source: agent-harness `core/skills/lessons-learned/SKILL.md`. Edit it there; this copy is generated.

Review the entire conversation history of this session and identify lessons learned. Read the
whole arc rather than sampling — friction you cannot see is friction you cannot diagnose.

Look for:

1. **Stale rules** (check this first — it is usually the highest-value category): did this session touch code that an existing rule describes *incorrectly*? Rules go wrong silently, because every session reinforces them and nothing contradicts them. If you read a rule's claim during this session and the code disagreed — a path that moved, a component that was renamed, a default that changed, a list that is now incomplete — that is a finding, even if it caused no visible problem this time.

2. **Repeated mistakes or corrections**: Did the agent make errors that the user had to correct? Could a rule have prevented this?

3. **Missing documentation**: Were there assumptions made that turned out wrong because documentation was missing or outdated? Suggest specific rule updates or doc additions.

4. **Hook opportunities**: Were there manual checks the user had to request that could be automated with a hook? If a hook already exists but didn't catch something, suggest how to improve its prompt.

5. **Pattern gaps**: Did the session reveal coding patterns, conventions, or architectural decisions that aren't documented in the rules?

6. **Security or quality concerns**: Were there any security, performance, or accessibility issues that slipped through? Could a preToolUse or postToolUse hook catch these?

7. **Wasted work**: look for concrete signals rather than a general impression —
   - the same file read more than once
   - tool calls whose output was never used in an answer
   - a subagent spawned for work that would have finished in a handful of direct calls
   - separate approval round-trips that could have been one batched question
   - a search or audit re-run because the first pass was scoped wrong

**Where rules live.** Every rule, skill and hook is generated by rulesync; the IDE folders
(`.claude/`, `.cursor/`, `.kiro/steering`, `.kiro/skills`) are copies. Project-specific sources
are in the project's `.rulesync/` folder; shared ones are in the agent-harness repo, with hooks in
its `core/hooks.jsonc` and the project's review checklist in `.rulesync/harness.json`. The
`> Source:` line at the top of each generated file names its source. Read and cite sources, and
propose changes to them, never to a generated copy.

**Pre-check, before writing any recommendation:**
Read the existing rules and hooks that relate to each candidate finding, and work out whether an existing rule or hook already covers it. Then:
- If an existing GENERAL rule already covers the finding (e.g. a reusability/shared-constants rule, a cross-cutting audit rule, an i18n rule), DO NOT propose a new narrower rule that restates it. Skip the finding, or at most suggest a one-line strengthening of the existing rule and name the exact file.
- If an existing hook already performs the check, DO NOT propose a new hook. Only suggest improving that hook's prompt if it demonstrably missed something this session.
- Only propose a NEW rule or hook when nothing existing covers the finding. Prefer extending an existing rule/file over creating a new one.
- For each finding, name the existing rule or hook you checked and say why it does or does not already cover the issue. A finding without that citation isn't ready to present.

For each finding that survives the pre-check, provide:
- What happened (brief)
- Root cause (why it happened)
- Whether existing rules/hooks already cover it (cite the file checked)
- Recommended fix — **the literal text to add, replace or delete**, with the target source file, and whether it belongs in the shared harness (true of any project) or the project's `.rulesync/` (true of this repo only). Not "tighten the i18n rule" or "improve the hook prompt": the actual wording, so the proposal can be read as a diff and accepted or rejected on sight. If the fix is a deletion, quote the text that should go.

Propose, don't apply. Present the findings and let the user choose which to act on.

**Rule quality guidelines:**
When recommending rules, follow these principles:
- Write rules as general, reusable principles — not tied to specific phases, sprints, or one-time tasks.
- Good: 'Never hardcode user-facing strings in component files. All shared values go in src/constants.ts.'
- Bad: 'src/constants.ts must be created in Phase 1 alongside types.'
- Good: 'State that must survive navigation belongs in a Context provider at the root layout level.'
- Bad: 'In Phase 2, remember to lift conversation state to a context provider.'
- Rules should apply every time the situation arises, not just the first time it was encountered.
- Avoid referencing build phases, sprint numbers, or session-specific context in rule text.
- Do not duplicate an existing rule in more specific language — a specific instance of an already-documented general rule is NOT a new lesson.
- If a rule only applies to a very narrow scenario that's unlikely to recur, skip it.
- Respect the context budget. The always-on rules are deliberately kept small. A new rule belongs in a path-scoped rule for the code it governs unless it genuinely applies to every request. Never propose a rule that restates what can be learned by reading the repo.
- Prefer project knowledge over generic quality advice. A rule earns its place by encoding something about *this* repo that cannot be derived from the diff — a registration step that is easy to miss, two files that must change together. Generic instructions ("write correct code", "check your work") add tokens without adding information.
- Count the existing checks before adding one. Between the end-of-turn review checklist and any wiring-review skill, a check may already run twice; a third copy makes the review longer, not better.
- **Propose removals as readily as additions.** A rule that is wrong is worse than a rule that is missing, because it is followed confidently. A rule that is dead, or that is a third copy of a check two hooks already run, costs tokens on every request and buys nothing. Deleting one is a legitimate finding — say which text should go and why.
- **No cosmetic proposals.** Do not suggest rewording, reordering, retitling or tone changes to a rule. Only propose a change that would alter what the agent actually does. Review noise is what stops these reviews from being read.

Evidence standards for these findings are the Evidence Discipline rules in the `agent-method` rule
(always loaded) — in particular, verify a claim about behaviour before presenting it, rather than
inferring it from a name or a search hit.

Prioritize findings by how much time they cost or risk they pose, and present the highest-value ones first. If the session was smooth with no notable issues, say 'Clean session — no lessons learned to capture.'
